## 阶段 3：分类管理（三层树 + 内联新增商家）

| 序号 | 任务 | 验收标准 |
|------|------|----------|
| 3.1 | 创建 `categories.py`，实现 `GET /api/categories`：返回带 `used` 标记的完整树（按 level 和 parent_id 组织） | 响应 JSON 包含所有分类及其 children，`used` 为 boolean（表示是否被记录引用） |
| 3.2 | 实现 `POST /api/categories`：新增分类（`name`, `parent_id` 可选）。若 parent_id 为空则为一级；若 parent_id 为二级则自动设 level=3；否则 level=parent_level+1。校验层级不超过 3 | 新分类插入数据库并返回 id |
| 3.3 | 实现 `DELETE /api/categories?id=`：仅当 `used=false` 且无子分类时允许删除（红=可删，灰=不可删） | 返回成功/失败及原因 |
| 3.4 | 实现 `POST /api/categories/reorder`：接收 `{ids, parent_id}` 更新同级排序 | 修改 `sort_order` 字段，前端重排后提交 |
| 3.5 | 前端记账页「场景」三级联动组件：一级下拉 → 二级 chips → 三级商家 chips。当选中二级且有商家时显示商家列表；无商家时显示「＋ 新增商家」 | 组件可展示完整树，选择叶子分类后记录 id |
| 3.6 | 前端新增商家弹窗：输入名称，调用 `POST /api/categories`（parent_id 为当前二级 id），成功后自动刷新分类树并默认选中新商家 | 商家永久保存，下次记账可直接选用 |

## 阶段 5：报表基础聚合（不含预算/余额，先实现核心统计）

| 序号 | 任务 | 验收标准 |
|------|------|----------|
| 5.1 | 创建 `statistics.py`，实现 `GET /api/report/aggregate` 的基础框架 | 接收 `month`（必选，格式 YYYY-MM）、可选 `category_id`、`motive`、`channel`、`is_weekend`、`period`、`month_part` |
| 5.2 | 实现 **时间特征派生**（查询层）：根据 date 和 time 计算 `is_weekend`、`period`、`month_part`，作为筛选条件 | 筛选逻辑正确（如 `period=上午` 只返回 time 在 6-12 的记录） |
| 5.3 | 实现 **总览聚合**：`total` 包含 `income`（amount>0 总和）、`expense`（amount<0 绝对值总和）、`balance`（全部 amount 总和） | 响应 `total` 正确 |
| 5.4 | 实现 **场景分解 `scene_breakdown`**：若未传 `category_id`，按一级场景汇总支出（amount<0）；若传一级，按该一级下所有子项（二级）汇总；若传二级，按该二级下商家（三级）汇总。收入不纳入场景统计 | 返回 `[{category_id, name, total}]`，实现下钻路径 |
| 5.5 | 实现 **消费场景分解 `scenario_breakdown`**：按 `motive_id` 分组支出（原 motive 语义为消费场景），返回 `独自/社交/为他人` 三组 | 响应 `scenario_breakdown` 数组 |
| 5.6 | 实现 **渠道分解 `channel_breakdown`**：按 `channel_id` 分组支出（全部金额，包括收入？文档要求“消费场景只对支出统计；余额用全部”，但渠道分解未明确，暂定按所有金额分组，但可标记方向） | 返回 `[{channel_name, total}]`（所有金额） |
| 5.7 | 实现 **记录明细 `records`**：返回匹配当前筛选的所有记录（含分类名、渠道名、场景名、金额等），供底部面板展示 | 按日期降序，分页可选（首版可返回全部） |
| 5.8 | 实现 **消费分布 `spending_dist`**：按一级场景（若未传 category_id）或叶子分类（若传了具体 category_id）列出金额降序，同时计算每个分类的记录数、中位数、平均数（仅对支出） | 返回 `[{category_id, name, total, count, median, avg}]`，无自动标记 |
| 5.9 | 前端报表页加载：默认显示本月数据，展示「总览卡片」（收入/支出/结余），「场景分解」用柱状或饼块展示（暂用 CSS 简单条），「消费场景分布」、「渠道分解」、「消费分布」列表 | 所有数据随月份切换刷新 |

## 阶段 6：预算与渠道余额（新增模块）

| 序号 | 任务 | 验收标准 |
|------|------|----------|
| 6.1 | 创建 `budgets.py`，实现 `GET /api/budget?month=`：返回当前用户该月所有一级场景的预算列表（含预算金额） | 若未设置，返回空或 0 |
| 6.2 | 实现 `POST /api/budget`：接收 `{category_id, month, amount}`，若已有该月该一级场景的预算则覆盖更新 `updated_at`，否则插入 | 重复设置成功，返回新预算记录 |
| 6.3 | 修改 `statistics.py` 的 `/api/report/aggregate` 响应，增加 `budget` 字段：对每个一级场景，计算实际支出（金额绝对值）与预算对比，给出 `budget_amount`、`actual`、`remaining`、`overspent`（boolean） | 超支高亮（前端可标记红色） |
| 6.4 | 创建 `balance.py`，实现 `GET /api/balance`：返回当前用户所有渠道的余额列表（id, name, balance） | 数据与 `dim_channel` 一致 |
| 6.5 | 实现 `POST /api/balance/calibrate`：接收 `{channel_id, balance}`，获取当前渠道余额作为 `before`，计算 `delta = balance - before`，更新 `dim_channel.balance = balance`，写入 `channel_calibrations` 记录（含 `before, after, delta, date=今天, note` 可空） | 校准成功后返回校准记录 id |
| 6.6 | 前端报表页添加「账户余额」模块：展示各渠道名称和当前余额，每个渠道旁附「校准」按钮，点击弹窗输入目标余额，调用校准 API 并刷新余额列表 | 校准后余额立即更新，历史记录可查（暂不展示，但 db 已存） |
| 6.7 | 前端报表页「预算执行」模块：按一级场景列表展示预算、实际、结余，超支高亮。点击某场景可展开或下钻至二级（或跳转），展示该场景下各子项的预算执行（若未设预算则显示0或“未设”） | 点击下钻需重新调用 API 并传递 `category_id` 来改变场景分解 |

## 附：贯穿始终的测试与质量保障

- 每个阶段完成后，建议进行**手动回归**，确保新增功能未破坏已有功能。
- 重点测试边界情况：
  - 金额为 0 或负数（支出）
  - 时间、日期格式异常
  - 渠道余额为负数（允许）
  - 分类删除时 used 检查
  - 预算覆盖更新
  - 校准记录 delta 计算
- 建议使用 SQLite 命令行工具随时查看数据一致性。
